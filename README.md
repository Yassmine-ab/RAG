# RAG over the vLLM codebase

[![CI](https://github.com/imyassmine/rag/actions/workflows/ci.yml/badge.svg)](https://github.com/imyassmine/rag/actions/workflows/ci.yml)
[![Python 3.10+](https://img.shields.io/badge/python-3.10%2B-blue)](https://www.python.org/)

**A Retrieval-Augmented Generation pipeline that answers natural-language questions about a
~1,900-file Python & Markdown codebase.** AST-aware chunking, TF-IDF / BM25 retrieval, grounded
answers generated by `Qwen/Qwen3-0.6B`, and a recall@k evaluation harness — exposed as a small CLI.

Built as the 42 Paris *"RAG against the machine"* project.

```
$ make run ARGS='answer "How to dynamically load a LoRA adapter?" --k 3'
To dynamically load a LoRA adapter, send a POST request to the
`/v1/load_lora_adapter` endpoint with the name and path to the LoRA adapter.
```

With the BM25 index, the top three retrieved chunks all come from `docs/features/lora.md`, which is
exactly the passage the evaluation dataset labels as the answer for this question.

## Results

Recall on the public 42 datasets (**100** documentation questions, **99** code questions), measured
with `max_chunk_size=2000` on 1,937 files (BM25: 19,067 chunks; TF-IDF: 18,298 after dropping chunks
under 50 characters; index built in ~6 s for TF-IDF, ~9 s for BM25):

| Retriever | Recall@5 docs | Recall@5 code | Recall@10 docs | Recall@10 code |
|-----------|:-------------:|:-------------:|:--------------:|:--------------:|
| TF-IDF    | 75.0%         | 51.5%         | 81.0%          | 61.6%          |
| BM25      | 79.0%         | 73.7%         | 88.0%          | 81.8%          |

A question counts as a hit when the reference passage appears in the top-k sources (same file,
IoU of character spans ≥ 0.05). Two retrieval changes drove most of the gain over the first version
of this project (TF-IDF: 64.0% docs / 35.4% code at recall@5): BM25 now tokenizes
`snake_case`/`camelCase` identifiers into separate words and indexes the file path, while TF-IDF uses
sublinear term frequency. Identifier-aware tokenization alone lifted code recall@5 from 35.4% to
65.7% — natural-language questions simply shared no token with compound identifiers before. The
remaining misses are questions with no lexical overlap with the code (see Roadmap).

## Quickstart

Requirements: Python 3.10+, [`uv`](https://docs.astral.sh/uv/).

```bash
git clone https://github.com/imyassmine/rag.git && cd rag
make install

# The corpus is not versioned: fetch vLLM 0.10.1 into data/raw/ (~38 MB)
mkdir -p data/raw
curl -sL https://github.com/vllm-project/vllm/archive/refs/tags/v0.10.1.tar.gz | tar -xz -C data/raw

# 1. Build the index (~9 s; BM25 gives the best recall — see Results)
make run ARGS="index --max_chunk_size 2000 --method bm25"

# 2. Retrieve the most relevant source snippets
make run ARGS='search "How to dynamically load a LoRA adapter?" --k 5'

# 3. Generate a grounded answer (downloads Qwen3-0.6B, ~1.5 GB, first run only)
make run ARGS='answer "How to dynamically load a LoRA adapter?" --k 3'
```

Without `make`: `uv run python -m src <command>`. Use `--method tfidf` at indexing time to switch
retriever — the method is stored in the persisted index, so search commands need no extra flag.

| Command | Description |
|---|---|
| `index --max_chunk_size 2000 --method tfidf\|bm25` | Chunk `data/raw/` and persist `data/processed/index.pkl` |
| `search "<question>" --k 5` | Print the top-k source locations |
| `search_dataset --dataset_path <json> --k 10` | Run retrieval over a question dataset |
| `answer "<question>" --k 5` | Retrieve then generate a grounded answer |
| `answer_dataset --student_search_results_path <json>` | Generate answers for a whole dataset |
| `evaluate --student_search_results_path <json> --dataset_path <json>` | Compute recall@k |

## How it works

```
data/raw/ (vLLM source)
   │
   ▼
chunking.py ──► indexer.py ──► data/processed/index.pkl (TF-IDF or BM25)
                                   │
question ──► retriever.py ─────────┘
                 │
                 ├──► top-k sources ──► generator.py (Qwen3-0.6B) ──► grounded answer
                 │
                 └──► evaluator.py ──► recall@k (IoU ≥ 0.05)
```

- **`chunking.py`** — Python files are split with `ast`, one chunk per top-level function/class
  (decorators included) and one for module-level code; Markdown files are split on headings. Any
  chunk above `max_chunk_size` is hard-split, and files with a syntax error fall back to fixed-size
  slicing.
- **`indexer.py` / `retriever.py`** — lexical retrieval. BM25 indexes each chunk together with its
  file path, tokenizing `snake_case`/`camelCase` identifiers into separate words and dropping stop
  words; TF-IDF uses scikit-learn with sublinear term frequency and cosine similarity.
- **`generator.py`** — builds a context-only prompt from the retrieved passages and runs Qwen3-0.6B
  with `enable_thinking=False` (direct answer, no reasoning trace). Chunk text is re-read from
  `data/raw/` using the stored character offsets, so an existing search-results file stays valid
  even if the index is rebuilt.
- **`evaluator.py`** — recall@k against the annotated datasets.
- **`models.py`** — Pydantic contracts shared by every stage (and used to validate dataset files).

## Testing & CI

```bash
make lint   # flake8 + mypy
make test   # 35 pytest tests: chunking, tokenizer, indexing/retrieval, recall metric, datasets
```

The GitHub Actions workflow runs lint, type-checking and the retrieval tests **without** installing
PyTorch (fast, < 1 min). A separate manual workflow (`workflow_dispatch`) runs the full pipeline
end-to-end on the real corpus, including one Qwen3 answer.

## Roadmap

- **Semantic retrieval**: embeddings + FAISS fused with the lexical retriever — the remaining misses
  are questions with no lexical overlap with the code, which no lexical retriever can fix.
- **Hybrid fusion + reranking**: Reciprocal Rank Fusion of TF-IDF and BM25 adds ~1 pt of docs recall
  over BM25 alone; a cross-encoder reranker (`ms-marco-MiniLM-L-6`) was measured too: +5 pts
  recall@5 on docs, no gain on code, ~5 s/query on CPU — worth revisiting once GPU/serving is set up.
- **Answer evaluation**: measure faithfulness / answer correctness (not only retrieval recall).
- **Serving**: wrap the pipeline in a FastAPI service and ship it with Docker.
